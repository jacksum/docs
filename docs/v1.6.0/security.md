# 安全运行 Pi \{#run-pi-safely}

把模型生成的命令和代码视为不受信任的内容。Pi 能以启动它的账号权限读取、修改和执行文件，并且不会在每次调用工具前都征求批准。扩展、包安装程序、语言服务器和其他子进程也以同样的权限运行，除非操作系统或虚拟化机制限制了它们的权限。

文件、注释、指令、命令输出和模型回复都可能通过提示词注入影响模型。项目受信任与否决定启动时会加载哪些项目资源，但不能保证这些内容或由此引发的操作是安全的。

要控制错误或恶意操作的影响，应限制 Pi 可以访问或影响的文件、凭据、进程和网络服务。查看会话记录、使用项目信任机制和审查改动都不能建立安全边界。

## 选择运行方式 \{#choose-how-to-run-pi}

不同的运行方式，对生成命令可访问内容的限制不同：

| Pi 的运行方式 | 仍受保护的内容 |
|---|---|
| 直接运行，使用当前操作系统用户的权限 | 该用户不能访问的内容。专用用户账号可以缩小权限范围，但 Pi 仍与其他用户共享操作系统和网络。 |
| 整体运行在容器、虚拟机或沙箱内 | 未暴露给隔离环境的宿主机文件和进程。在环境内提供的凭据和网络服务仍可访问。这通常是实际可用的方式中隔离最强的一种。 |
| Pi 在隔离环境外运行，只有内置工具在隔离环境中执行 | 通过这些工具发起的操作无法访问受保护的宿主机资源。Pi 本身和其他扩展仍在隔离边界之外，因此保护范围更小。 |

工作目录决定从哪里发现资源，以及工具默认在哪个位置操作。它无法阻止命令访问 Pi 进程可以访问的其他路径。

无论选择哪种方式，都只提供任务需要的文件和服务。尽可能把凭据留在环境之外，或使用权限范围小、有效期短的凭据。命令不需要网络时，请限制网络访问。

各隔离方式的配置步骤和限制见[在隔离环境中运行 Pi](./containerization.md)。

## 项目受信任机制 \{#understand-project-trust}

项目受信任与否决定 Pi 是否加载工作目录提供的大部分设置和资源。这样可以避免在你批准前，文件夹中的可执行扩展被静默加载。

项目信任机制无法保护启动过程的每一步。Pi 会在选择或创建会话时读取项目的 `sessionDir` 设置，此时还没有判定项目是否受信任。拒绝信任可以阻止其余项目设置和受保护资源的加载，但无法撤销最初的会话目录查找。

项目信任机制不会限制工具调用可访问或影响的内容。Pi 启动后，已启用的工具仍以 Pi 进程的操作系统权限运行。文件夹内的指令及其他内容也能影响模型。

### 受项目信任机制保护的资源 \{#resources-protected-by-project-trust}

如果 Pi 根据当前工作目录发现以下任一资源，就需要判定项目是否受信任：

- `.pi/settings.json`
- `.pi/mcp.json`
- `.pi/extensions`、`.pi/skills`、`.pi/prompts` 或 `.pi/themes`
- `.pi/SYSTEM.md` 或 `.pi/APPEND_SYSTEM.md`
- 当前目录或任一父目录中的项目 `.agents/skills`

仅有一个 `.pi` 目录不需要判定项目是否受信任。

信任项目后，Pi 可以加载：

- 项目设置
- `.pi/mcp.json` 中的项目 MCP 服务器
- `.pi` 下的扩展、技能、提示词模板、主题和系统提示词文件
- 项目设置中配置但尚未安装的包
- 项目本地扩展和项目包中的扩展

拒绝信任会跳过这些受保护资源，前文所述的首次 `sessionDir` 查找除外。

除非关闭上下文加载，否则 `AGENTS.override.md`、`AGENTS.md` 和 `CLAUDE.md` 等上下文文件都会加载，无论项目是否受信任。即使拒绝信任项目，也应将文件夹中的指令视为不受信任的输入。

### 信任判定的优先顺序 \{#how-pi-chooses-a-trust-decision}

命令行中的 `--approve` 或 `--no-approve` 优先。发现受保护资源且命令行未覆盖时，按以下顺序判定：

1. 用户级扩展和通过命令行加载的扩展可以处理 `project_trust` 事件。第一个返回肯定或否定结果的扩展决定是否信任。
2. 如果没有扩展作出决定，Pi 会查找当前目录或其父目录中已保存的决定，采用离当前目录最近的一项。
3. 如果没有适用的已保存决定，Pi 会遵循全局设置 `defaultProjectTrust`，其默认值为 `"ask"`。

已保存的信任决定使用规范化的目录路径，存放在：

```text
~/.pi/agent/trust.json
```

用 `/trust` 保存决定，供之后启动的 Pi 进程使用。

### 无交互提示时的项目受信任机制 \{#project-trust-without-an-interactive-prompt}

输出、JSON 和 RPC 模式都不能显示内置的信任提示。若没有适用的命令行覆盖、扩展或已保存的决定：

- `defaultProjectTrust: "always"` 会加载受保护的项目资源。
- `defaultProjectTrust: "ask"` 或 `"never"` 会跳过这些资源。

自动化运行需要明确作出一次性信任决定时，使用 `--approve` 或 `--no-approve`。

## 降低影响并保留恢复手段 \{#reduce-impact-and-improve-recovery}

以下做法不能替代隔离，但能降低暴露范围，或让出错后的恢复更容易：

- 只让 Pi 访问任务需要的文件和服务。
- 进行较大改动前，使用快照、备份或版本控制。
- 加载扩展和包之前先审查它们。扩展在 Pi 进程内执行。
- 优先使用权限范围小、有效期短的凭据。
- 将结果应用到其他系统之前，审查差异和生成内容。
- 导出或分享前检查会话。会话可能包含提示词、工具参数、命令输出、文件内容和对话中暴露的凭据。

## 报告安全问题 \{#report-a-security-issue}

遵循仓库的[安全政策](https://github.com/earendil-works/pi/blob/main/SECURITY.md)。不要用公开 issue 报告敏感的安全问题。

本地智能体的预期行为、不受信任内容引发的提示词注入、缺少内置沙箱，以及用户自行安装的扩展或技能产生的行为，通常不属于安全报告范围。例外是报告能证明存在权限边界绕过，或能取得本地用户原本没有的访问权限。
