# TUI 核心渲染器：显式历史与视口契约 \{#tui-core-renderer--explicit-history-and-viewport-contract}

本文档描述 `@oh-my-pi/pi-tui`
（`packages/tui`）的终端渲染器契约。相关实现位于：

- [`packages/tui/src/term/backend.ts`](https://github.com/can1357/oh-my-pi/blob/c9730fdb620ce4599dd898691e3e3b56003bfcb5/packages/tui/src/term/backend.ts)：
  终端后端，负责帧合成、提交前沿、历史批次、
  自然流式输出、视口分配、重放和关闭时刷新。
- [`packages/tui/src/driver/output/writer.ts`](https://github.com/can1357/oh-my-pi/blob/c9730fdb620ce4599dd898691e3e3b56003bfcb5/packages/tui/src/driver/output/writer.ts)
  ：帧写入器，负责历史追加、视口差异比较、同步输出、
  调整大小时的借用与锚点恢复、故障即停。
- [`packages/tui/src/driver/contract.ts`](https://github.com/can1357/oh-my-pi/blob/c9730fdb620ce4599dd898691e3e3b56003bfcb5/packages/tui/src/driver/contract.ts)：
  `FramePlan` 和 `TerminalDriver`，两者之间的接缝。
- [`packages/tui/src/text/markdown/render.ts`](https://github.com/can1357/oh-my-pi/blob/c9730fdb620ce4599dd898691e3e3b56003bfcb5/packages/tui/src/text/markdown/render.ts)
  ：流式 Markdown 及其稳定头部。
- [`packages/tui/src/host.ts`](https://github.com/can1357/oh-my-pi/blob/c9730fdb620ce4599dd898691e3e3b56003bfcb5/packages/tui/src/host.ts)：宿主生命周期
  （启动、挂起、优雅停止）。

应用代码负责会话记录生命周期。渲染器不会检查节点
内容来猜测哪些行已经最终确定。其模型采用 Elastic Speculative
Slots 协议（[论文](https://stencil.so/blog/harness-playbook/elastic-slots.pdf)）；
`packages/tui/test/term/elastic-slots.test.tsx` 和
`packages/tui/test/driver-output/elastic-slots.test.ts` 会依据该协议检查后端和
写入器。

## 1. 帧的归属 \{#1-frame-ownership}

程序描述一个 `Surface`（`packages/tui/src/surface.ts`）：`main`（按顺序排列的
会话记录）、`dock`（其下方的实时界面元素）和 `layer`（覆盖层）。
程序通过 `settle(node)` 决定最终性；没有其他机制会将块标记为
最终确定。每一帧中，后端都会绘制各区域，并向驱动提交一个
`FramePlan`：

```ts
interface FramePlan {
	readonly history?: { readonly id: number; readonly rows: readonly string[]; readonly kind?: "append" | "replay" };
	readonly viewport: readonly string[];
	readonly cursor: { readonly row: number; readonly col: number } | null;
	readonly fullscreen?: readonly string[];
}
```

`viewport` 是本帧完整的可变屏幕图像。`append`
历史批次包含整块退役的已确定块的行，或
流式块稳定头部的行。`replay` 批次包含当前宽度下的
完整账本：所有已提交块，然后是同一帧中退役的所有内容
（其中包括受空间压力影响的流式头部稳定行）。

历史批次具有单调递增的 id。写入器
写入后，`present()` 才返回该 id（确认）；在此之前，后端会持续提供同一批次，
绝不复用 id 或改变其顺序。尚未写入的批次一旦被丢弃，之后绝不会
再以原 id 写入，因此后端可以将其丢弃并重新准备：
自绘制以来宽度发生变化、所写块
不再紧随提交前沿、显示再次丢失
（`onReplay`），以及关闭时刷新，都会触发这种处理。

每个 `main` 节点的块状态：

- **活动**：尚未确定，每帧重新绘制，只出现在视口中，但
  流式节点的稳定头部除外；
- **已确定**：已最终确定但仍驻留于实时视口，会按当前宽度重新绘制（因此
  调整大小会使其重新排版），直到行空间压力使其退役。压力只会移走
  不再能容纳的行：实时尾部顶端的已确定块可以
  部分位于历史中，其他行仍驻留并重新绘制（工具卡片
  可以在其历史行下方折叠）；
- **已提交**：整块已写入历史并获确认。已提交块始终是
  `main` 的一个前缀（提交前沿），按提交顺序排列。在已提交块
  上方（或部分位于历史中的块上方）插入块、移除
  该块，或改变已提交块的位置，都会重放历史，因此每个
  块都会按顺序写入一次。

流式头部：绘制器可以报告 `Block.stable`，即后续
输入不再能改变的前导行（带 `stream` 的 `md`，编码智能体的助手
外观）。此保证具有单调性：一行一旦报告为稳定，源文本无论怎样
扩展都不会改变该行。Markdown 通过以下方式维持这一点：在当前写入文本仍可能
并入的块之前结束头部（空行后相同标记的列表项可能继续列表，
缩进行可能继续缩进代码）；在尚未闭合的
独立数学公式起始标记（行首的 `$$`、`\[`、`\begin{`）之前结束头部；以及
仅根据每个块之前的定义解析该块的引用链接
（包括开放尾部，因此行不会依赖文档有多少内容已经
确定）。在行空间压力下，只有第一个活动块可以将行移入
历史（已确定块的行，或流式块的稳定头部），且只移动
压力所要求的数量；随首批行写入的分隔符也计入其中，
而且可能只有分隔符被移走。

后端会记住已写入的该块的行，并在每一帧检查
该块是否仍以这些行开头；如果块仍然改变了这些行（所谓稳定头部
其实并不稳定，或关闭 `stream` 后采用不同的最终
渲染），则会重放历史。宽度不同时，行无法匹配，
但不会因此重放：历史中的前缀（以其写入时的宽度
为准）会根据字母和数字映射到新宽度下的行，因此换行
和填充不会产生影响（内容全部已在历史中的前导行
不会进入视口；回到写入时的宽度时，不做
映射）。在段落内部切开的块会重复该行文字一次；在块
之间切分则能精确映射。当驱动在调整大小时保持历史的旧宽度
（`TerminalDriver.replaysOnResize()` 为 false：`preserve` 或就地
调整大小），压力只会移动完整块和完整稳定头部，因此每个切分
都位于块之间；如果仍无法映射（块发生了变化），则会重放。

## 2. 渲染一帧 \{#2-rendering-a-frame}

每一帧，后端都会：

1. 绘制停靠区；屏幕剩余高度就是 `main` 的空间。
2. 让提交前沿之后最短的已确定前缀退役，以使
   活动尾部能够容纳，或移走第一个活动块的稳定行。退役
   在第一个活动状态块处停止。
3. 在活动块之间分配空间（第 2.1 节）。
4. 在视口上合成各层，并将方案交给驱动。

驱动确认批次后，后端会提交其块，并请求
另一帧：该批次等待期间变得符合条件的内容会在
那时退役。

写入器（`FrameWriter`）：

1. 在视口起始位置将尚未确认的历史批次
   追加恰好一次，然后确认其 id。空视口下的历史批次
   以一个空行结束，光标停在该行上，因此下一帧或
   shell 绝不会覆盖最后一行历史。
2. 将可变视口锚定在历史紧下方。
3. 规范化各行并使其适配宽度，关闭自动换行，只写入变化的行。
4. 在同步输出帧内停放硬件光标。

历史和视口有不同的更新规则。历史是有序
追加流；视口行可以替换。重放是一次写入：清除
（用于 `rebuild`/显示重置）与重放的账本及视口合并完成。
不会观察到逐块重放帧。

没有同步输出时（Terminal.app 忽略 DEC 2026），终端可能
呈现一帧写入内容的任意前缀，因此这些帧绝不会重绘那些
只是移动了的行。即将离开屏幕的行会先显示其历史
行，底行的换行会将其推入滚屏历史，保留的行
通过 DL/IL 移到相应位置（绝不在顶行执行删除，因为 Terminal.app
会将其归档到滚屏历史），最后只重写仍存在差异的行。每个
中间屏幕都是上一帧的滚动或平移结果，绝不会出现一行
与其陈旧副本并排，或已擦除的条带等待重绘。包含图片或
OSC 66 文本的帧仍使用普通的逐行重写路径。

可见覆盖层是屏幕坐标内容。它们合成在
视口之上，绝不会进入历史。

写入器采用故障即停机制：输出目标的写入一旦抛错，就会永久停止（不再进行后续
写入，也不确认失败的批次），并重新抛出异常。进程
驱动也会在 stdout 失败或停滞时停止。

### 2.1 视口分配 \{#21-viewport-allocation}

活动尾部能够容纳时，会完整显示。尾部更高时，按最新
优先分配：每个活动状态块至少保留一行，最新块获得
剩余空间，已确定块只获得最后剩下的空间。分配行数少于自身
行数的块，会按该高度绘制（`paint(node, width, height)`：工具外观会绘制
紧凑呈现），如果其绘制器忽略高度，则截取
尾部。当活动状态块数量超过行数时，最新的 `rows - 1` 个块各保留
一行，上面显示汇总行（`⋯ N more running`，统计更早的、
有绘制内容的活动状态块；会绘制其中最新的一批，至少 16 个，来
判断是否有内容，更早的则视为有绘制内容）。分配绝不会使任何内容退役、
确定或取消。

绘制器报告为 `Block.covering` 的停靠区行（输入编辑器的补全
弹窗）会绘制在会话记录之上，而不是占用其空间：
`main` 的空间保持不变，其下方活动行只是隐藏，而不是退役。

视口一旦到达屏幕底部，就会在那里保持高度：
活动内容缩小时，活动主区域行与停靠区之间的空行
会让停靠区保持在底部。这些行不是活动行：退役和
分配都不会计算它们。重放和调整大小会重置此状态；全屏
层会使常规屏幕及固定视口保持原样。

### 2.2 全屏屏幕模式 \{#22-fullscreen-screen-mode}

`TermBackendOptions.screen`（`HostOptions.screen`；编码智能体的
`tui.screen`）选择会话绘制位置：`inline`（上述所有行为）或
`fullscreen`。全屏帧是 `FramePlan.fullscreen` 帧：
写入器在整个会话期间保留备用屏幕，常规屏幕
保持原样。

- 停靠区按行内模式绘制并固定在底行，即使
  会话记录很短也是如此；`main` 在一个窗口中填充其上方的行。块按
  自然高度绘制（即行内历史所容纳的内容）：无分配、无汇总
  行、无退役、无历史批次。各层合成在帧之上；
  全屏层会替换它，与行内模式相同。
- 窗口跟随尾部，或锚定到某个 `main` 节点及其
  条目中的一行（先计算其分隔行）。锚定窗口下方的输出绝不会使
  它移动。滚动条显示位置，不占用会话记录行。
  关闭滚动条时，如果空间允许，最后一行显示 `↓ N lines below`。
  停靠区开头的空白填充会让位于会话记录行。如果从锚点起的行
  都能容纳（滚动到末尾、屏幕变高、下方块
  被移除），则再次跟随尾部；若锚点行超出已缩小的块，
  则将其限制在有效范围；锚点节点离开 `main` 时，则跟随尾部。
- `TermBackend.scroll(by)`（`Host.scroll`）按一页（窗口高度减
  一行）、指定行数、到 `start` 或到 `end`（跟随）移动。没有窗口显示在
  屏幕上时（行内模式、全屏层已打开、Tern）返回 false，因此
  调用方的按键会交给其他位置处理。逐行、半页和按用户提示语义跳转的操作
  使用同一个窗口。滚轮报告使用自动或固定步长；模态
  面板保留自己的输入处理。右边缘滚动条跟踪视口。
- 全屏模式请求 SGR 按钮移动和焦点报告。拖动会选择
  会话记录单元格，双击选择单词，三击选择行，
  在边缘按住会将选择范围扩展到屏幕之外。复制通过
  应用的剪贴板输出目标完成（OSC 52 和本地平台辅助程序）。
- `Host.openSearch()` 打开增量式会话记录查找，不会将查询
  文本放入编辑器。匹配项会高亮；Enter 和 Shift+Enter 循环
  切换匹配项，Escape 恢复阅读位置和草稿。行内和原生
  宿主不接受会话记录操作。
- 关闭时刷新之前，任何内容都不会进入历史；刷新会合成常规的
  行内帧：写入器离开备用屏幕，将提交前沿之后的每个块
  写到会话开始位置下方。设置
  `tui.exitTranscript: false` 时，全屏模式退出不执行此刷新。紧急
  恢复绝不会调用应用绘制器：如果会话已进入持久存储，崩溃报告器会在
  清理后打印恢复命令。
- 提交前沿在运行时切换模式后仍然保留：行内模式
  已提交的块保持已提交，全屏阶段不提交任何内容，下一个
  行内帧从前沿开始使块退役，因此每个块都进入历史
  一次。
- 如果此前只有全屏帧（常规屏幕上没有我们的内容），一次
  稳定后的大小调整会重绘而不是重放，显示重置会完整重绘
  备用屏幕而不是清除：这类会话绝不会清除
  原生历史。`Host.suspend()` 恢复时不会重置显示，除非
  曾写入历史；下一帧会再次进入备用屏幕。

## 3. 重置与调整大小行为 \{#3-reset-and-resize-behavior}

`Host.replayHistory()`（`driver.resetDisplay()`）清除终端历史和
屏幕，并重放账本：其后一帧会携带一个采用
新 id 的 `replay` 批次。普通渲染绝不会清除历史；只有历史
不再匹配账本（在历史上方插入块、重排或移除块、
某个块在同一宽度下的历史行发生变化），以及停止后
重新启动（`Host.suspend`：终端所持内容未知）时，后端才会
自行请求重放。

调整大小会使视口几何信息失效，并按新的
宽度和高度重绘视口。大小调整稳定后，写入器会应用滚屏历史
策略（`tui.resizeScrollback`、`PI_TUI_RESIZE_SCROLLBACK`）：

- `rebuild` 清除原生历史，并重放一份当前宽度的会话记录；
- `append` 保留原生历史，在宽度变化时追加一份当前宽度的会话记录
  （仅高度变化不会追加副本）；
- `preserve` 只重绘视口，让旧宽度的历史保持原样，
  绝不清除它（参见第 1 节的文字映射）。

高度缩小时，程序收到通知之前，屏幕顶部行就可能被推入滚屏历史。
写入器会推算终端推走了哪些视口行
（先是光标下方的空行，然后是顶部行），根据
锚点恢复的光标报告验证该模型，只有验证后，才会在
下一历史批次以这些行开头时不再重复写入（如果报告
位于别处，或同一轮连续调整中出现第二步，则仍会写入：可能重复，绝不会
丢失）。

底层默认值为 `preserve`；编码智能体设为 `rebuild`。重放保留
提交前沿，只在写入返回后才确认。

就地调整大小（默认用于多路复用器/ConPTY 之外的 Warp，或通过
`PI_TUI_RESIZE_IN_PLACE=1` 强制启用）会跳过大小调整重放，在拖动
稳定后重绘。`PI_TUI_RESIZE_IN_PLACE=0` 强制使用借用缓冲区路径。
参见[运行时大小调整细节](./tui-runtime-internals.md#resize)。

渲染器绝不会探测用户的滚动位置。

### 3.1 关闭 \{#31-shutdown}

`Host.stop()` 会在归还终端前刷新
（`TermBackend.flush()`）：最后一帧将每个活动的 `main` 块按其
当前状态（无论是否已确定）写入历史，接在待处理重放尚未
写出的账本之后，并将停靠区保留为视口。写入器尚无法进行行内写入时
（大小调整借用、静默大小调整、锚点探测），或者驱动因
输出积压而跳过该帧时，写入器会保留该帧，并在驱动停止时
从视口顶部写入。`Host.suspend()`
不刷新：程序恢复时会重放显示。

## 4. ANSI 与宽度不变量 \{#4-ansi-and-width-invariants}

`visibleWidth`、`truncateToWidth`、`sliceByColumn` 和 `wrapTextWithAnsi` 共享
同一个感知 ANSI 的 UAX#11 宽度模型。测量、切片、截断和换行
都必须通过这些辅助函数进行，使转义序列保持零宽，
并使列边界一致。

- 可打印 ASCII 使用每个代码单元占一个单元格的快速路径。
- 非 ASCII 文本使用共享的歧义字符窄宽模型，并共享
  感知终端/平台的 Hangul Compatibility Jamo 宽度修正。
- 制表符使用 `DEFAULT_TAB_WIDTH`。
- OSC 66 定尺寸片段按其声明的单元格宽度计入。
- 过宽行会截断到视口宽度；渲染热路径不得
  因外观上的宽度不匹配而抛出异常。

ANSI 状态会在行边界规范化，使独立更新的行保持
有效。光标写入保持在同步输出内、ESU 之前，以避免
第二个可见帧。

## 5. 终端能力与输入探测 \{#5-terminal-capabilities-and-input-probes}

终端检测选择同步输出、DECCARA
和图片协议等优化；不会改变历史语义。

在 tmux 内，窗格环境标识的是 tmux，而不是所连接的
模拟器。启动时，终端检测会向本地 tmux 服务器查询
`#{client_termtype}` 和 `#{client_termname}`，并通过
常规能力表映射已识别的名称：先使用终端类型响应，再使用能够
标识其模拟器的客户端 `TERM`（`xterm-kitty`、`xterm-ghostty`、`wezterm`）。窗格
自身的 `TERM`（`tmux-*`）绝不会选择图片协议；无法识别的客户端
会将图片支持交给运行时 SIXEL 探测。修饰按键仍需要 tmux
`extended-keys`，而 OSC 通知和 Kitty 图形需要
`allow-passthrough`。

`ProcessTerminal` 将能力查询与带类型的 DA1 哨兵所有者配对。
私有 CSI 响应可能跨多次 stdin 刷新拆分，因此重组必须保留
部分响应直到终止符出现，并且不得将探测字节泄漏为用户
输入。新探测需要带类型的哨兵所有者，以及按字节拆分响应的
测试覆盖。

SIXEL 发现接受肯定的 XTSMGRAPHICS 几何响应或 DA1
属性 4。`ProcessTerminal.onSixelSupport` 在消费响应字节并保留哨兵归属的同时，
发布并缓存 DA1 宣告。
缺少 DA1 属性不会否定 XTSMGRAPHICS 报告的支持。
根据 DA1 选择 SIXEL 不会结束待处理的 XTSMGRAPHICS 查询：其输入
消费器会保留到图形响应到达或探测超时。
显式 `PI_FORCE_IMAGE_PROTOCOL` 选择，包括 `none`/`off`，具有优先权；
原生 TSP 表面保留自己的图片传输机制。

### 原生渲染（Tern Surface Protocol） \{#native-rendering-tern-surface-protocol}

`ProcessTerminal` 还会在 `tsp`
DA1 哨兵所有者之后发送 TSP `hello` 查询（APC `tsp`）。`PI_TUI_NATIVE=0` 禁用它；多路复用器、devenv 的
重新加载 shell（`DEVENV_RELOAD_FILE`：其终端层转发 DA1，但丢弃
APC）以及 Bun 测试默认跳过它，而 `PI_TUI_NATIVE=1` 强制执行探测
（tmux 仍需要 `@tern-tsp`）。在 `TERM_PROGRAM=tern` 下，只有多路复用器的
会话标记才算数，单独的 `screen*`/`tmux*` `TERM` 不算，并且调试日志
会记录一次窗格为何仍采用行渲染。支持版本的
响应会将 `TUI` 切换到 `native/backend.ts`：组件
会被描述（`describe()`，或来自 `render()` 的 `rows` 回退），协调
为文档操作（`native/reconcile.ts`），并作为帧发送，节奏由
终端确认而非渲染频率控制。回显用户输入的帧
（按键、粘贴，或 Tern 为节点报告的任何 UI 事件：点击、
切换、`edit`、…）可以在额度之外再发送两帧，只计算
未获确认时间不足 250 ms 的帧，使受控编辑器在 Tern
缓慢确认流式会话记录时仍能持续回显
输入，并显示按钮点击的效果（例如被其关闭的表单离开
屏幕）。此余量是速率，而不是总量：Tern 保持静默时，输入
每 250 ms 最多发送 `credits + 2` 帧，直到
5 s 停滞重置；每次回显都携带所有因
额度限制而暂存的变化。其他帧会等待确认或该重置。本文档的
历史、视口、大小调整重放或 CPR 机制均不会在此路径上运行；
SIGWINCH 只刷新 `rows` 回退节点所用的宽度。表面
活动期间，会在进程本地强制采用 nerd 符号预设，图标字形
作为 `icon` 片段发送。首次行绘制最多等待
300 ms 以完成探测。直接 Tern 会话会乐观地立即打开表面，
如果终端未确认，则回退为行渲染。此类
会话从一开始就需要原始输入，因此 `deferInput` 启动不会使
tty 停留在规范模式。其他终端在模块图加载期间用于显示输入的
内核回显，在这里改由 Tern 提供：输入编辑器的 `editor` 节点
携带 `typeahead: true`（`Editor.nativeTypeahead`，由 `Composer.start` 设置），
Tern 会保留输入其中的文本，在插入光标处绘制，并在
该属性清除时，或在第一个它不保留的按键之前，将其按输入时的形式写入
pty。启动期间到达 omp 的输入（来自此类刷新，或没有预输入功能的
Tern）会在 TUI 中分流：普通输入（可打印文本、Backspace）
会实时编辑启动时获得焦点的组件；第一个其他按键（快捷键、
Enter、方向键、粘贴）及之后的每个按键都会按输入顺序暂存。
其间获得焦点的对话框（启动 hook 的选择或确认）会实时收到
输入；从这类对话框打开外部编辑器而触发 TUI 停止/启动时，
暂存状态仍会保留。替换进来的自定义编辑器通过 `Composer.setEditor()`（`TUI.replaceHeldFocus()`）继承暂存状态和
预输入，因此
其按键会排在已暂存按键之后，并保留启动提交门控。
单元格尺寸响应仍在到达时被消费，TSP 终端上会跳过 sixel 探测，
因此没有探测监听器会看到暂存的按键。`InteractiveMode.init()`
在启动 hook、模式协调、草稿
恢复及所有会话订阅完成后，紧接着解除提交门控之前，调用 `Composer.releaseHeldInput()`：
清除 `typeahead`，让 Tern 发送保留的内容；恢复的草稿放在
启动期间输入的文本之前；启动快捷键作用于最终已被观察的
会话；暂存的 Enter 仍会被忽略。Ctrl+C/Ctrl+D 会提前释放 TUI 的
队列。
调试套接字的 `doc` 操作返回参考文档
（由 `native/apply.ts` 应用每个已发送帧），而 `tsp` 返回最近的帧。

#### 显式输入编辑器提交 \{#explicit-composer-submission}

omp 的 `q: "hello"` 宣告 `features: ["edit", "undo", "send"]`。
`editor`/`input` 属性 `sendable` 与文本可编辑性独立：
`sendable: true` 表示所有者已准备好接受原子提示提交。
该值缺失或为 false 即表示未就绪，即使字段可写或已获得焦点也是如此。
基础 `Editor` 和 `Input` 字段发布 false，因为它们不处理 `send`。
提示输入的 `CustomEditor` 只有在其 `onSubmit` 处理器存在，
且 `disableSubmit` 为 false 时才发布 true。

在交互式引导启动期间，输入编辑器保持可写，但为 `sendable: false`。
所有处理器和订阅就绪后，初始化会解除提交门控，
并请求一次渲染以发布 `sendable: true`，无需用户输入。
终端必须保留待提交提示，直到该就绪更新到达；
不得提前分发、休眠、轮询或延迟模拟的 Enter。

终端看到 `"send"` 和就绪的输入编辑器后，可以通过
`e` 消息提交所提供的提示：

```json
{ "ev": "send", "sf": "s:1", "id": "k.line/input", "text": "First line\nSecond line" }
```

`sf` 必须指向活动表面，`id` 必须指向其可编辑的输入编辑器节点（
`omp.editor` 角色下的 `editor` 后代，通常为 `<component>.line/input`），
而不是输入编辑器包装节点或其发送按钮。三个载荷字段都是
必填字符串；表面和节点 id 必须非空。格式错误的载荷、
未知或已关闭的表面，以及过期/不可编辑的目标节点都会被忽略。
终端在分发已宣告的 `send` 事件之前，还必须要求目标节点上的
`sendable === true`。后端解析节点所有者并交付
`{ type: "send", key: "line/input", text }`，与键盘焦点无关。

`CustomEditor` 通过其普通的 `submit()` /
`onSubmit` 路径提交该文本一次。多行文本仍是一个提示；常规的已加载文本
规范化、外围空白去除、命令处理、主智能体与当前查看
智能体之间的路由，以及已提交历史规则仍然适用。这不是粘贴：
大型提示不会打开大段粘贴选择菜单，而且终端
不得在该事件后跟随模拟的 Enter。空文本或仅包含空白的
文本不执行操作，绝不会提交现有草稿或中断流。
已禁用或尚未连接好处理器的输入编辑器同样不会改变草稿。

非空白发送替换草稿前，旧文本、粘贴展开内容和
附件会保存在本地回忆历史中（不会作为已提交
提示持久化）。显式载荷会单独提交，不带这些旧
附件或粘贴展开内容。发送会在输入 FIFO 中等待所有
进行中的剪贴板/附件工作结束，包括失败，因此
被替换的草稿只会在其待处理附件全部到达后才保存。
原生发送按钮操作保持原有行为：它们提交
当前草稿，而不是显式载荷。

## 6. 行内图片与内存 \{#6-inline-images-and-memory}

Kitty 图片只传输一次，可放置多次。`ImageBudget` 只保留
最近的图片；降级会按 id 删除图片像素，并使用
保留高度的文本回退重绘受影响的视口行。它不会重放
历史。已保留在终端历史中的图片在
降级时可能失去像素，因为历史行不可变。

在全屏会话记录中，视口会裁切 Kitty 放置区域和 SIXEL 条带。
OSC 1337 没有源矩形：被裁切的 iTerm2 图片会保留空间，
完全可见时重新出现。面板不能被其下方的
非单元格图形穿透。缓冲区切换会使备用屏幕上的放置失效；
优雅关闭时的会话记录刷新会在常规屏幕上重新创建符合条件的图片。

绝不要每帧重新传输完整的 base64 图片数据。Kitty Unicode
占位符仍受能力门控，并可通过现有的
图片环境设置覆盖。

## 7. 核心不变量 \{#7-core-invariants}

1. 程序决定最终性（`settle`）；只有已确定块和声明为稳定的
   头部，才会通过有序历史批次进入历史。
2. 每个批次恰好写入一次，并按 id 确认；已提交块
   是 `main` 的前缀，每个块的行都按顺序在历史中出现一次
   （重放在新的纪元中重写整个账本）。
3. 稳定行绝不会改变；流式头部的历史行会在
   每帧验证，任何不匹配都会触发重放。
4. 普通帧只比较并重绘视口。它们绝不会重写、
   审计或清除保留的历史。
5. 行数允许时，每个活动状态块都保留一个视口行；溢出内容
   会被汇总，绝不会退役。
6. 只有显式显示重置、`rebuild` 大小调整和账本不匹配
   才会破坏性地清除原生历史，而且只有我们的行已经出现在
   常规屏幕上时才会这样做（只有全屏帧的会话绝不会如此）。
7. 写入失败会停止写入器；优雅停止会刷新会话记录。
8. 宽度处理使用共享的感知 ANSI 的辅助函数，并在渲染热路径中进行限幅，
   而不是抛出异常。渲染器绝不会探测滚动位置。
