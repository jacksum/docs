# Vibe 模式 \{#vibe-mode}

Vibe 模式将顶层交互式会话变为持久后台工作会话的**指挥者**，而不是让它自己编辑或执行命令。指挥者的活动工具缩减为 `read`、可选的由父会话管理的 `todo`，以及五个工作会话控制工具。工作会话负责搜索、编辑、运行和构建；指挥者通过读取改动过的文件来验证它们的说法。父会话管理主待办列表；工作会话通常不包含 `todo`，除非其自身的预先遍历交接需要它。

## 启用与禁用 \{#enabling-and-disabling}

使用 `/vibe` 斜杠命令切换：

```text
/vibe                 # enter vibe mode
/vibe fix the flaky test in packages/tui    # enter and submit a first directive
/vibe                 # run again to exit
```

- 进入时，激活父会话的工作会话作用域，安装 vibe 工具，将活动工具集缩减为 `read`、可选的由父会话管理的 `todo` 和 vibe 工具，并注入指挥者指令。
- 内联提示词（`/vibe <prompt>`）会进入该模式，并将该提示词作为第一条指令提交。
- 退出时，中止正在运行的指挥者轮次，在拆除期间抑制排队消息的重放，恢复之前的工具集，取消进行中的工作会话轮次，并为该作用域中的每个工作会话持久化终态生命周期记录。
- Vibe 模式与活动**及已暂停**的计划/目标模式互斥；请先退出这些模式。
- Vibe 模式启用期间，会拒绝启动、删除、分叉、移动（包括 `/wt`）或交接会话。重置式 `/loop` 操作也会被阻止。
- 模式开启时，状态行显示 `Vibe` 指示器；其 token 速率显示会汇总正在生成内容的工作会话，即使指挥者处于空闲状态也一样。

`/vibe` 是交互式 TUI 命令。模式与工作会话生命周期事件随父会话一起持久化。恢复当前模式为 `vibe` 的会话时，会将已完成的工作会话连同其子会话记录重建为空闲/停驻会话；因进程重启而中断的轮次不会自动恢复。被显式终止或因模式退出而终止的工作会话仍保持终态。

切换到已保存的会话会挂起来源作用域：正在运行的工作会话轮次会被取消，排队指令会被清空，但持久化的子会话不会被标记为删除。返回该父会话时可以重建它们；这与主动退出 `/vibe` 不同。

## 两种工作会话层级 \{#the-two-worker-tiers}

每个工作会话都是一个真正的、保持存活的任务执行子代理，具有常规编码工具接口，以及自身持久化的子会话记录。创建时选择层级：

| 层级 | 内置智能体 | 默认角色 | 适用场景 |
| --- | --- | --- | --- |
| `fast` | `sonic` | `@smol` | 机械性执行、草稿、大批量工作 |
| `good` | `task` | `@task` | 设计、判断决策，以及审查 `fast` 的输出 |

层级始终选择内置的 `sonic` 或 `task` 定义，而不是发现的同名自定义智能体。其他模型解析行为与任务智能体路由一致：`task.agentModelOverrides.sonic` / `.task` 优先于内置智能体模型，角色别名通过 `modelRoles` 解析，并以父会话的活动/默认模型作为回退。

## 工作会话控制工具 \{#worker-control-tools}

| 工具 | 输入与行为 |
| --- | --- |
| `vibe_spawn` | `{ cli: "fast" \| "good", prompt, name? }`。以完整、自包含的首份任务说明启动空白工作会话。`name` 会被清理并限制为 48 个字符；省略时生成一个 id。 |
| `vibe_send` | `{ session, message }`。在流式轮次的下一步对其进行引导；如果存在轮次但无法引导，则排入自动开始的下一轮；如果处于空闲/停驻状态，则立即开始下一轮。 |
| `vibe_wait` | `{ sessions?, timeout? }`。等待被观察的轮次中第一个结束（省略时观察所有进行中的工作会话），默认 30 秒。它会确认已结束的作业，避免重复交付其结果。 |
| `vibe_kill` | `{ session }`。取消进行中的轮次，清空排队消息，释放工作会话，并将已初始化的会话记录保留在 `history://<id>`。 |
| `vibe_list` | `{}`。按创建顺序列出会话，包含层级、状态、轮次/队列计数、解析后的模型和近期活动。 |

创建和发送操作会立即返回。每个工作会话轮次的结果都会通过异步作业管理器自动交付到指挥者对话中；长响应文本在其中会受预览长度限制，完整输出可通过 `agent://<id>` 获取。让 `fast` 和 `good` 工作会话同时处理独立工作流是常规用法。

当某个工作会话轮次无法接受引导时，排队的多条消息会合并为一条自动开始的下一轮指令。`vibe_list` 会从实时列表中省略被显式终止的工作会话，并单独报告其 id；`vibe_wait` 仍可观察显式指定的、已结束的工作会话。

## 作用域与失败行为 \{#scope-and-failure-behavior}

工作会话 id 的作用域限定在所属智能体和父会话内；来自其他作用域的工作会话会被报告为未知，且无法控制。创建需要会话异步作业管理器。创建失败会终止尚未完全创建的工作会话；生命周期持久化失败时可能保留一条死亡记录，以便模式退出时恢复处理。轮次失败会以失败作业结果的形式自动交付，而可恢复的保活工作会话会返回 `idle`，等待下一次 `vibe_send`。轮次结束时，如果工作会话的子会话不再处于同一所有者作用域下的空闲/停驻状态，该工作会话就会变为 `dead`。发送操作会拒绝过期或不匹配的子会话身份，而不是控制另一个会话。

## 工作流程 \{#workflow}

1. 将请求拆分为独立工作流，每个工作流使用一个持久工作会话，使其各自积累有用的对话上下文。
2. 调用 `vibe_spawn` 并提供自包含的任务说明：文件、约束和可观察的验收标准。工作会话从空白状态开始，从不会看到指挥者的对话。
3. 轮次进行期间，继续指挥其他工作会话。受阻时才使用 `vibe_wait`；等待超时后可以再次发起。
4. 自然地使用 `vibe_send` 进行纠正并给出后续步骤。在轮次中途发送时，能引导就进行引导；否则自动成为工作会话的下一轮。
5. 结果到达时，使用 `read` 读取改动过的文件；预览不足时检查完整输出。通过可选的父会话 `todo` 汇总已验证的工作。
6. 按难度路由：用 `fast` 起草，机械性执行停滞或需要判断时升级到 `good`。
7. 对已完成或卡住的工作会话使用 `vibe_kill`。退出该模式会终止整个剩余作用域。

指挥者仍负责最终结果：工作会话完成意味着轮次已结束，而不是其说法正确。
