# Vibe 模式 \{#vibe-mode}

Vibe 模式让顶层交互式会话成为持久后台工作会话的**调度者**，由工作会话负责编辑文件或执行命令，而不由顶层会话直接操作。调度者可用的工具仅有 `read`、可选的由父会话管理的 `todo`，以及五个工作会话控制工具。工作会话负责搜索、编辑、运行和构建，调度者通过读取涉及的文件核实其报告。主待办列表归父会话管理；工作会话通常不使用 `todo`，除非自己的预遍历交接需要它。

## 启用和退出 \{#enabling-and-disabling}

用斜杠命令 `/vibe` 切换模式：

```text
/vibe                 # enter vibe mode
/vibe fix the flaky test in packages/tui   # enter and submit a first directive
/vibe                 # run again to exit
```

- 进入模式时，系统激活父会话的工作会话作用域，安装 Vibe 工具，将可用工具缩减到 `read`、可选的由父会话管理的 `todo` 和 Vibe 工具，并注入调度者指令。
- 在同一行附带提示（`/vibe <prompt>`）会进入该模式，并将该提示作为第一条指令提交。
- 退出时，系统中止调度者正在运行的轮次，在清理期间禁止重放排队消息，恢复之前的工具集，取消工作会话正在运行的轮次，并为该作用域内每个工作会话持久化终态的生命周期记录。
- Vibe 模式与处于活动状态**或暂停状态**的计划模式和目标模式互斥。请先退出这些模式。
- Vibe 模式启用时，不允许启动、删除、派生、移动（包括 `/wt`）或交接会话。重置类的 `/loop` 操作也会被阻止。
- 模式启用时，状态栏会显示 `Vibe` 指示标记。即使调度者空闲，状态栏上的 token 生成速率也会汇总正在生成内容的工作会话的数据。

`/vibe` 是交互式 TUI 命令。模式和工作会话的生命周期事件会随父会话持久化。恢复当前模式为 `vibe` 的会话时，已完成的工作会话会作为空闲或已停驻的会话重新载入，并带有各自的子会话记录。因进程重启而中断的轮次不会自动继续。显式终止或因退出该模式而终止的工作会话保持终态。

切换到已保存的会话会挂起源会话的作用域：正在运行的工作轮次会被取消，排队的指令会被清空，但持久化的子会话对话不会添加删除标记。返回原父会话时，可以重新载入这些子会话。这和主动通过 `/vibe` 退出模式不同。

## 两个工作会话档位 \{#the-two-worker-tiers}

每个工作会话都是一个持续存活、实际执行任务的子代理，拥有常规的编码工具和独立持久化的子会话记录。启动时选择档位：

| 档位 | 随附的智能体 | 默认角色 | 适用任务 |
| ------ | ------------- | ------------ | --------------------------------------------------- |
| `fast` | `sonic` | `@smol` | 机械性操作、起草、大批量工作 |
| `good` | `task` | `@task` | 设计、需要判断的决策、审查 `fast` 的产出 |

档位始终选择随附的 `sonic` 或 `task` 定义，不使用发现的同名自定义智能体。其余模型解析规则与任务智能体路由一致：`task.agentModelOverrides.sonic` / `.task` 优先于随附智能体的模型，角色别名通过 `modelRoles` 解析，回退选项是父会话的当前模型或默认模型。

## 工作会话控制工具 \{#worker-control-tools}

| 工具 | 输入和行为 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vibe_spawn` | `{ cli: "fast" \| "good", prompt, name? }`。启动一个没有既有上下文的工作会话，并提供一份完整、可独立理解的初始任务说明。`name` 会经过清理，最多保留 48 个字符；省略时会生成 ID。 |
| `vibe_send` | `{ session, message }`。在流式轮次的下一步引导该轮次；如果轮次存在但无法引导，则排队等待自动启动下一轮；如果工作会话空闲或已停驻，则立即启动下一轮。 |
| `vibe_wait` | `{ sessions?, timeout? }`。等待受监视的轮次中第一个结束（未指定会话时监视所有正在运行的工作会话），默认等待 30 秒。确认已结束的任务，避免重复投递结果。 |
| `vibe_kill` | `{ session }`。取消正在运行的轮次，清空排队消息，释放工作会话，并在 `history://<id>` 保留已初始化的会话记录（如有）。 |
| `vibe_list` | `{}`。按启动顺序列出各会话及其档位、状态、轮次数和排队数、解析后的模型及最近活动。 |

启动和发送操作会立即返回。每个工作轮次的结果都会由异步任务管理器自动投递到调度者的对话。投递的预览文本有长度上限，可在 `agent://<id>` 查看完整输出。通常让 `fast` 和 `good` 档的工作会话并行处理各自独立的工作。

一个工作轮次无法被引导时，多条排队的消息会合并成下一轮自动执行的一条指令。`vibe_list` 不在实时列表中显示显式终止的工作会话，而是单独报告其 ID。`vibe_wait` 仍可监视明确指定的、轮次已结束的工作会话。

## 作用域和失败行为 \{#scope-and-failure-behavior}

工作会话 ID 的作用域由所属智能体和父会话共同限定。来自其他作用域的工作会话会被报告为未知，无法控制。启动工作会话需要会话的异步任务管理器。启动失败时，系统会终止未完整启动的工作会话。如果生命周期记录持久化失败，系统可能保留一条终止状态的记录，以便在退出模式时恢复处理。轮次失败会自动投递为失败的任务结果，可恢复且持续存活的工作会话则会回到 `idle`，以接收下一次 `vibe_send`。轮次结束时，如果工作会话的子会话不再在同一所有者作用域内处于空闲或已停驻状态，该工作会话会变为 `dead`。发送操作会拒绝过期或不匹配的子会话身份，避免控制另一个会话。

## 工作流程 \{#workflow}

1. 将请求拆成彼此独立的工作。每项工作分配一个持久的工作会话，以便各自积累有用的对话上下文。
2. 调用 `vibe_spawn`，提供一份可独立理解的任务说明，包含文件、约束和可观察的验收标准。工作会话从空白开始，不会看到调度者的对话。
3. 在轮次运行期间继续调度其他工作会话。仅在无法继续时使用 `vibe_wait`，等待超时后可以再次调用。
4. 直接用 `vibe_send` 发送纠正指令和后续步骤。在轮次中发送的消息会尽可能引导当前轮次，否则会自动进入该工作会话的下一轮。
5. 收到结果后，用 `read` 查看涉及的文件。预览不足以核实时，查看完整输出。可以用父会话可选的 `todo` 同步已核实的进度。
6. 按难度分配工作：用 `fast` 起草，机械性操作遇阻或需要判断时转交给 `good`。
7. 用 `vibe_kill` 终止已经完成工作或停滞的工作会话。退出该模式会终止作用域内所有剩余的工作会话。

调度者仍对最终结果负责。工作会话完成仅表示轮次已结束，并不表示它的报告正确。
